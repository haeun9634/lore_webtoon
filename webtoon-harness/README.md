# webtoon-harness

스토리 파이프라인의 **"컷 서술 → 실제 웹툰 이미지"** 구간만 검증하는 실험 도구입니다.
제품이 아닙니다. UI/DB/서버 없습니다. 자동 선택도 없습니다 — 전부 저장하고 사람이 고릅니다.

서버가 없으므로 사람의 판단은 전부 **파일**로 돕니다. 브라우저에서 고치고 →
내려받아 → 같은 폴더에 저장하면, 다음에 다시 만들 때 그 파일이 HTML 안에 박혀
들어와 기준선이 됩니다 (`file://` 에서는 fetch 를 쓸 수 없기 때문입니다).

| 파일 | 무엇을 담나 | 어디서 고치나 |
| --- | --- | --- |
| `picks.csv` | 어느 후보를 채택했나 | 컨택트 시트 |
| `layout.json` | 컷별 표시 크기 | 컷 뷰어 |
| `bubbles.json` | 말풍선 글자 자리 | Scene 뷰어 |
| `cast.json` | 컷마다 주인공이 나오는가 | 텍스트 편집기 (초안은 자동 생성) |
| `supporting.json` | 조연의 외형·성별 | 텍스트 편집기 (초안은 자동 생성) |
| `feedback.json` | 무엇이 잘못됐는가 — 그림 / 스토리 / 종합 | **`review.html`** (컨택트 시트에서도 가능) |
| `style_faces.json` | Scene 별 얼굴 자리 (크롭) | 그림체 화면 |
| `style_score.csv` / `verify_score.csv` | 사람이 매긴 Y/N | 그림체 / 통합 검증 화면 |

기록만 하는(사람이 고치지 않는) 파일도 같은 폴더에 쌓입니다:

| 파일 | 무엇을 담나 |
| --- | --- |
| **`episode.png`** | **결과물.** Scene 을 세로로 이어 붙인 웹툰 1화 한 장 |
| **`review.html`** | **읽으면서 피드백 남기는 화면.** 자동 생성 |
| `log.jsonl` | 호출 하나 = 한 줄. 프롬프트·첨부·응답·토큰·비용 전부 |
| `usage.csv` | 호출 하나 = 한 줄, 추적에 필요한 열만 (표 계산기로 열어 보는 용도) |
| `usage.json` | 화 전체 합계 — 종류별 / 모델별 / 조건별, 비싼 호출 5건 |

## 후보 장수 (`--candidates`)

| 값 | config.yaml | 기본 |
| --- | --- | --- |
| 컷당 후보 | `candidates_per_cut` | **1** |
| Scene 당 후보 | `scene.candidates_per_scene` | **1** |
| 통합 검증 후보 | `scene.verify_candidates_per_scene` | 2 |

**기본이 1장인 이유.** 후보를 여러 장 뽑는 것은 *그중에서 고르려고* 하는 일이고,
그건 **조건 비교 실험**(A vs S vs D 중 어느 쪽이 일관된가)에서만 의미가 있습니다.
한 화를 만드는 것이 목적이면 고를 것이 없습니다 — 같은 프롬프트로 같은 모델에서
3번 뽑으면 미묘하게 다른 그림 3장이 나올 뿐이고 비용만 3배입니다.

Scene 모드는 특히 그렇습니다. 한 장 안에 컷이 여러 개라 "이 장은 2번 컷은 좋은데
3번 컷이 별로"가 되어서 **장 단위로는 고를 수가 없습니다.**

조건을 나란히 놓고 비교할 때만 올리세요 (`--candidates 3`).

`--candidates N` 은 **셋을 한 번에** 덮어씁니다 (이번 실행에만, config 파일은 그대로).

```bash
python run.py --run-id <id> --episode 1 -c S+ --candidates 3   # 조건 비교할 때만
```

**후보가 1장이면 채택 단계를 건너뜁니다.** `picks.csv` 가 없어도 `--view` 와
`--style-lock` 이 `c1` 을 채택본으로 봅니다 (고른다는 말 자체가 성립하지 않으므로).
조건 `S+` / `D` 의 "직전 장" 체인도 그 유일한 결과를 그대로 씁니다.
후보를 2장 이상으로 올리면 예전처럼 컨택트 시트에서 골라야 합니다.

## 명령 하나로 1화 (`make_episode.py`)

```bash
python make_episode.py --character characters/siha.json --style cinematic
python make_episode.py --run-id <id> --style cinematic      # 이어서
```

스토리 → 캐릭터 시트 → 콘티 → 그림 → `episode.png` 를 순서대로 돕니다.
**이미 끝난 단계는 건너뜁니다** — 중간에 실패하면 고치고 같은 명령을 다시
치면 그 지점부터 이어집니다.

순서를 코드에 넣은 이유는 외우기 귀찮아서가 아니라, **어긋나면 조용히 틀린 것이
나오기 때문**입니다. 시트를 안 뽑고 컷으로 가면 지난 run 의 시트가 붙었고,
그림체를 시트보다 나중에 바꾸면 시트와 컷이 다른 그림체를 가리켰습니다.

### 사람을 부르는 자리는 둘뿐입니다

| 언제 | 왜 |
| --- | --- |
| **블라인드 평가** | 재미 판정은 이 파이프라인에서 사람만 하는 일입니다. 재미없는 설계로 컷을 잘 뽑아도 재미없는 웹툰이 나옵니다 |
| 시트 후보가 **여러 장**일 때 | 고를 것이 있을 때만 부릅니다. 1장이면 `story.py` 가 자동으로 채택합니다 |

멈추면 무엇을 하면 되는지와 어떤 명령으로 이어지는지를 화면에 찍고 종료 코드
`2` 로 끝냅니다. 나머지는 물어보지 않습니다 — 후보도 1장이고 채택도 없습니다.

## 조건 고르기 (`-c`) — 매번 하나는 골라야 합니다

`-c` 는 **무엇을 첨부할지**를 고르는 것입니다. 이 하네스가 "레퍼런스를 붙이면
인물이 실제로 일관되게 나오는가"를 재는 도구라서, 실행할 때마다 조건을 지정해야
합니다. **조건은 시트를 만들지 않습니다 — 만들어 둔 것을 가져다 씁니다.**

| 조건 | 첨부 | 필요한 시트 | 언제 |
| --- | --- | --- | --- |
| `A` | 없음 | — | 그림체·연출만 먼저 볼 때. 인물은 컷마다 달라집니다 |
| `S` | 통합 시트 1장 | `sheet` | **기본 경로.** `--charsheet` 를 `--split` 없이 돌리면 이게 나옵니다 |
| `S+` | 통합 시트 + **직전 장** | `sheet` | 장 사이 인물이 이어져야 할 때 (조연 포함) |
| `C` | 4면도 1장 | `turnaround` | `--split` 으로 따로 뽑았을 때 |
| `C+` | 4면도 + 표정 + 디테일 | 3종 전부 | 첨부를 늘리면 실제로 좋아지는지 잴 때 |
| `D` | 4면도 + 직전 장 | `turnaround` | `C` 의 이어짐 판 |

시트를 요구하는 조건(`S` `S+` `C` `C+` `D`)은 **그 run 의 시트가 없으면 멈춥니다.**
멈출 때 "지금 있는 시트로 바로 돌 수 있는 조건"을 알려 주니 그대로 쓰시면 됩니다.

시트는 story-harness 에서 먼저 만듭니다:

```bash
cd C:\lore\story-harness
python story.py --charsheet --run-id <id>          # 통합 시트 1장 → 조건 S / S+
python story.py --charsheet --run-id <id> --split  # 3장 따로   → 조건 C / C+ / D
python story.py --charsheet --run-id <id> --pick   # 채택 (이걸 해야 다음이 됩니다)
```

시트를 뽑기 **전에** `config.yaml` 의 `style_default` 를 그 화에 쓸 그림체로
맞추세요 — story-harness 에는 `--style` 이 없어서 그 값을 읽습니다.

## 그림체 고르기 (`--style`)

`config.yaml` 의 `styles:` 에 이름을 붙여 등록해 두고 이름으로 고릅니다.

```bash
python run.py --run-id <id> --episode 1 -c S+ --style webtoon    # 일반 웹툰
python run.py --run-id <id> --episode 1 -c S+ --style romance    # 로판 표지 일러스트
python run.py --run-id <id> --episode 1 -c S+ --style cinematic  # 시네마틱 반실사
python run.py --run-id <id> --episode 1 -c S+ --style lineart    # 선화 · 액션
python run.py --run-id <id> --episode 1 -c S+ --style pastel     # 일상툰 감성체
python run.py --run-id <id> --episode 1 -c S+ --style noir       # 다크 느와르
python run.py --run-id <id> --episode 1 -c S+ --style shoujo     # 순정만화 / BL풍
python run.py --run-id <id> --episode 1 -c S+ --style flat       # 기존 실험 값
```

생략하면 `style_default` 를 씁니다. 고른 문구는 코드가 모든 프롬프트에 강제로
붙습니다 — 문구를 명령줄에 직접 적을 수는 없습니다. story-harness 의
`--charsheet` 도 같은 표를 읽으므로, **두 하네스가 같은 이름을 쓸 수 있어야**
"시트와 컷이 같은 그림체인가" 를 대조할 수 있기 때문입니다.

| 이름 | 무엇 |
| --- | --- |
| `webtoon` | 일반 웹툰(네이버 웹툰 풍) — 균일한 깔끔한 선, 셀 채색(밑색 + 그림자 1단), 눈 하이라이트 1~2개, 배경은 단색·톤·최소한의 사물, 동세는 효과선으로 |
| `romance` | 로판 표지 일러스트 — 홍채를 여러 겹으로 쌓고 하이라이트 3~4개, 머리카락 광택 띠 여러 줄, 레이스/자수/보석 하나하나, 배경에 장미·빛번짐·금박 |
| `cinematic` | 고퀄 웹툰 + 시네마틱 반실사 — 방향이 분명한 키라이트와 림라이트, 공기 중의 빛(헤이즈·먼지·블룸), 얕은 심도와 보케, 필름 컬러그레이딩, 7등신 비율, 얼굴은 웹툰 그대로 |
| `lineart` | 선화 — 톤을 거의 안 쓰고 흰 여백을 그대로 남깁니다. 채워지는 건 머리카락(검정)과 옷(단일 톤)뿐이고 살결·배경·금속은 흰 종이. 액션 컷용 (`monochrome_styles` 에 등록돼 있어 눈·안깃·문양만 색으로 남습니다) |
| `pastel` | 일상툰 감성체 — 흔들리는 손그림 선, 열린 형태, 종이 결, 선 밖으로 삐져나온 색, 채도 낮은 대여섯 색. **덜 완성돼 보이는 것 자체가 스타일** (일상·학원·코미디) |
| `noir` | 다크 느와르 — 화면 대부분이 먹으로 덮이고 명암은 4단으로 뭉갭니다. 하드에지 그림자 덩어리(블라인드살·창틀·난간), 붓과 먹번짐, 거의 무채색 + 강조색 하나 (헌터·스릴러·액션·다크판타지) |
| `shoujo` | 순정만화 / BL풍 — 길고 날카로운 눈, 각진 턱선, 9등신, 스크린톤 점망 음영, 흐르는 머리카락, 여백에 그려 넣은 꽃과 반짝임. 얼굴 클로즈업과 두 사람 사이의 거리가 주제 (오메가버스·센티넬·BL) |
| `flat` | 기존 실험 값 (flat colors / minimal shading). 이전 결과와 비교하려면 필요합니다 |

**`romance` 와 `cinematic` 은 화려해지는 방식이 다릅니다.**

| | 무엇으로 화려한가 | 배경이 무엇인가 |
| --- | --- | --- |
| `romance` | **장식** — 장미·금박·레이스·보석 | 무대 장치 |
| `cinematic` | **빛** — 역광·공기·심도·색보정 | 실제 공간 |

그래서 둘을 섞지 마세요. `cinematic` 에 장미와 금박을 넣으면 그냥 `romance` 가
되고, 그 순간 "실제로 거기 있는 사람"이라는 이 그림체의 근거가 사라집니다.
`cinematic` 문구에 *"never from ornament pasted on top"* 이 들어 있는 이유입니다.

**반실사는 사실적으로 그리라는 뜻이 아닙니다.** 비율과 빛은 사실을 따르고
**얼굴은 웹툰으로** 둡니다. 얼굴까지 사실적으로 가면 캐릭터 시트와 어긋나고,
한국 웹툰 독자가 읽는 얼굴이 아니게 됩니다.

`webtoon` 은 나머지 둘과 **반대 방향**입니다 — "덜 그리는 것"이 스타일이고
기준은 읽히는 속도입니다.

**나중에 붙인 셋도 각자 "무엇으로 화면을 만드는가"가 다릅니다.** 이 축이
겹치는 순간 두 그림체는 같은 그림이 됩니다.

| | 화면을 만드는 재료 | 붙으면 안 되는 것 |
| --- | --- | --- |
| `pastel` | **손자국** — 흔들리는 선, 종이 결, 어긋난 색 | 깔끔한 닫힌 선·셀 채색(→ `webtoon`), 림라이트·보케·반짝임(→ `cinematic`/`romance`) |
| `noir` | **검은 덩어리** — 뭉갠 명암, 하드에지 그림자, 먹번짐 | 흰 여백과 얇은 선(→ `lineart`), 부드러운 감쇠·심도·블룸·색보정(→ `cinematic`) |
| `shoujo` | **선과 스크린톤** — 점망 음영, 여백, 그려 넣은 꽃 | 보석 눈·금박·레이스·풀컬러 장식(→ `romance`) |

특히 `noir` 와 `lineart` 는 **정반대**입니다. `lineart` 는 화면이 밝고
(살결·배경이 흰 종이) 검정은 머리카락과 옷에만 쓰지만, `noir` 는 화면이 어둡고
(대부분이 먹) 흰 곳이 소수의 빛뿐입니다. `noir` 와 `cinematic` 도 빛을 다루는
방식이 다릅니다 — `cinematic` 은 실제 렌즈의 빛을 **흉내내고**(감쇠·심도·보케),
`noir` 는 그림자를 **도형으로 그립니다**(감쇠 없이 딱 끊기는 검은 덩어리).

**`pastel` · `noir` · `shoujo` 는 `monochrome_styles` 에 넣지 않았습니다.** 셋 다
색이 적지만 무채색은 아닙니다. 그 훅이 프롬프트 맨 끝에 박는 문장은
*"BLACK INK ON WHITE PAPER … inked line art"* 라서 (`scenegen.MONO_TAIL`),
켜는 순간 `pastel` 의 파스텔은 지워지고 `noir` 는 흰 종이 선화로 뒤집히고
`shoujo` 는 딱 한 자리 남겨 둔 강조색까지 잃습니다. 채도를 죽이는 일은 각
그림체의 `COLOUR` 문구가 직접 합니다.

**이름은 그림체 낱말로만 짓습니다.** story-harness 의 장르 이름(`romance` ·
`idol` · `hunter` · `academy` · `fantasy` · `daily` · `martial` · `action` ·
`thriller` · `comedy` · `sentinel` · `omegaverse` · `gamefantasy`)과 겹치면
`--style romance` 가 그림체를 가리키는지 장르를 가리키는지 알 수 없어집니다.
`romance` 는 이미 겹쳤고 그건 남겨 둔 빚입니다 — 새로 만들 때는 겹치지 마세요.
그래서 일상툰을 `daily` 가 아니라 `pastel` 로, BL풍을 `omegaverse` 가 아니라
`shoujo` 로 등록했습니다.

문구가 길고 집요한 것은 실수가 아닙니다. "glossy detailed eyes" 정도로 줄이면
모델이 곧바로 평범한 웹툰 얼굴로 돌아갑니다. 홍채를 몇 겹 쌓는지, 빛이 어디서
들어오는지까지 적어야 그 그림이 나옵니다.

같은 화를 두 style 로 뽑아 `--style-lock` 으로 나란히 보면 그림체 차이가 바로
보입니다. **조건 비교 도중에 style 을 바꾸면 이전 실험과의 비교가 깨집니다.**

### 시트가 그림체를 이깁니다 — 순서 주의

첨부한 레퍼런스 이미지는 `style_suffix` 보다 강합니다. 시트가 사실적 얼굴이면
문구를 아무리 고쳐도 매 컷이 시트를 따라갑니다. 그래서 **순서가 중요합니다**:

1. `config.yaml` 의 style 문구를 먼저 확정한다
2. **조건 A(레퍼런스 없음)** 로 1~2컷만 뽑아 그 문구만의 결과를 본다
   — 시트가 안 붙으므로 문구의 힘이 그대로 보입니다
3. 문구가 마음에 들면 story-harness 에서 **그 문구로 캐릭터 시트를 다시 뽑는다**
4. 시트를 채택한 뒤에 조건 S+ 로 본편을 뽑는다

3번을 건너뛰고 바로 본편으로 가면 새 문구와 옛 시트가 서로 다른 그림체를
가리킵니다. `meta.json` 의 `charsheet.style_suffix` 대조 경고가 이걸 잡아 줍니다.

### 한 장에 몇 컷을 묶을까 — 픽셀로 계산되는 문제

Gemini 는 **호출당 이미지 1장**입니다. 그래서 "한 번에 N컷 생성" 은 곧 **한 장에
N칸**이고, 캔버스 세로 2400px(9:16 · 2K)를 N으로 나눈 것이 컷 하나의 크기입니다.

| 한 장에 | 13컷 기준 호출 | 비용 | **컷당 세로 픽셀** |
| --- | --- | --- | --- |
| 1컷 (`--mode cut`) | 13 | 2,439원 | 2400px |
| 2컷 (기본) | 7 | 1,313원 | 1200px |
| 3컷 | 5 | 938원 | 800px |
| 5컷 | 3 | 563원 | 480px |
| 10컷 | 2 | 375원 | 240px |

**많이 묶을수록 싸지고, 한 장 안에서는 확실히 통일되고, 대신 컷이 작아집니다.**
얼굴이 작다는 느낌은 800px 아래에서 나오기 시작합니다. 10컷은 통일은 되겠지만
바스트샷도 안 나옵니다.

컷 수를 정하는 값은 두 개입니다:

- `scene.cuts_per_scene` — 연출(W7.5)이 **없는** run 의 예비 경로
- `scene.max_cuts_per_scene` — **상한.** 연출이 있는 run 에도 걸립니다. 연출이
  정한 경계는 살리되 너무 커진 묶음만 잘라 나눕니다

값을 바꾸면 `scenes.json` 캐시가 자동으로 무효화됩니다.

**장 사이가 흔들린다면 묶음을 키우기 전에 `-c S+` 를 먼저 쓰세요.** 묶음을 아무리
키워도 마지막 묶음과 다음 묶음 사이에는 똑같은 경계가 남습니다 — 그 경계를 잇는
것이 `S+`(직전 장 첨부)입니다. 조연은 캐릭터 시트가 없어서, 이전에 그려진 모습을
보여 주는 것 말고는 얼굴을 이어 붙일 방법이 없습니다.

컷을 크게 하면서 많이 묶고 싶으면 진짜 레버는 `provider.options.image_size` 입니다
(`2K` → `4K` 로 올리면 컷당 픽셀이 2배). 다만 장당 단가가 오를 수 있으니 요금표를
먼저 보세요.

### 컷마다 바뀌는 작화 (`render_style`)

실제 웹툰은 한 화 안에서 그림체가 고정되지 않습니다 — 진지한 컷은 정식 작화로,
분위기 푸는 컷은 SD(2~3등신)로 그립니다. W7 이 컷마다 정한 `render_style`
(`normal` | `sd` | `emphasis`)마다 **통째로 다른 style 문구**를 씁니다:

```yaml
styles:
  romance:
    normal:   정식 로판 작화 (표지 일러스트 수준)
    sd:       2~3등신, 얼굴 극단 단순화, 파스텔 배경, 별·하트
    emphasis: 배경 제거, 집중선, 채도 대비 강하게
  webtoon:
    normal:   정식 웹툰 작화 (셀 채색, 깔끔한 선)
    sd:       2~3등신, 음영 없는 플랫, 별·땀방울
    emphasis: 배경 제거, 집중선 + 망점, 선 굵게
```

공통 문구 + 접미사 구조가 아닙니다. sd 컷은 로판 문구를 **아예 보지 않습니다** —
그렇지 않으면 셋이 결국 같은 그림체로 보입니다. 인물이 컷마다 조금 달라 보이는
것은 의도된 것입니다.

`normal` 이 그 style 의 대표값이고, 캐릭터 시트 대조에 쓰입니다. 문자열 하나짜리
style(`flat`)은 예전처럼 공통 문구 + `render_style_suffix` 로 동작합니다.

Scene 모드는 컷 여러 개가 한 장에 구워지므로, 묶인 컷이 **전부 같은**
`render_style` 일 때만 적용합니다. 섞여 있으면 `normal` 로 둡니다 — 한 컷 때문에
페이지 전체가 SD 가 되는 편이 더 나쁘기 때문입니다.

**SD 컷의 캐릭터 시트** — 시트는 정식 작화로 그려져 있어 SD 를 방해합니다. 빼면
머리색·의상까지 잃으므로, 붙이되 `sheet_notes.sd` 가 "색과 의상만 참조하고 얼굴
양식과 등신은 따르지 말라"고 못박습니다.

## 컷마다 달라지면 안 되는 것들

한 화를 뽑아 보면 인물이 컷마다 흔들립니다. 원인은 셋인데 서로 다릅니다.

### 옷 (`outfit_lock`)

`p1.json` 의 `appearance_en` 은 사진 여러 장에서 만들어집니다. 사진마다 옷이
다르면 이렇게 요약됩니다:

> "…**usually seen in** black off-shoulder tops, white shirts with plaid
> ribbons, black cropped tops with jumpers, **or** black training jackets"

이 문장이 모든 프롬프트 맨 앞에 강제로 붙습니다. **코드가 컷마다 "이 넷 중
아무거나"라고 말하는 셈**이라 옷이 매번 바뀝니다. 실제로 그렇게 나왔습니다.

`config.yaml` 의 `outfit_lock` 에 **한 벌만** 적으면 코드가 프롬프트 끝에
"이것만 입는다 / 위의 나열은 무시하라 / 장면이 갈아입었다고 말할 때만 바꾼다"
를 박습니다. 같은 자리에 들어가는 `design_details` 는 실제로 지켜지는 것이
확인됐습니다 — 피어싱과 목걸이는 컷마다 유지됐고 옷만 흔들렸습니다.

### 조연 (`supporting.json`)

주인공은 캐릭터 시트가 지켜 줍니다. 조연은 지켜 주는 것이 **하나도 없었습니다.**
콘티가 남기는 기록이 이게 전부였기 때문입니다:

```json
{"name": "시하의 동기 (이름 미정)", "note": "몰래 찍어 소문을 퍼뜨린 학과 동기"}
```

이름과 메모뿐, 외형이 없습니다. 그리고 이미지 프롬프트가 조연에 대해 말하는
것은 조건 문구의 한 줄 — *"주인공과 다르게만 그려라"* — 이 전부였습니다.
머리색도 키도 옷도 성별도 아무도 정해 주지 않으니 매번 새로 만듭니다.

이제 인물 카드가 **스토리에서 만들어져 명부에 쌓이고 그림까지 내려옵니다.**

| 항목 | 무엇 | 왜 따로인가 |
| --- | --- | --- |
| `gender` | male / female | 이것만 있어도 성별이 뒤집히는 건 막힙니다 |
| `appearance` | **안 바뀌는 것만** — 머리·눈·키·체형·특징 하나 | 끝까지 고정 |
| `outfit` | **늘 입는 옷 한 벌** | 옷은 장면에 따라 바뀔 수 있어서 외형과 분리 |
| `personality` | 표정·자세로 드러나는 성격·버릇 | 얼굴이 밋밋하게 나오는 걸 막습니다 |

`appearance` 와 `outfit` 을 **나눈 이유**: 한 칸에 뭉쳐 두면 그리는 쪽이 둘을
구분하지 못해 옷을 바꾸려다 머리색까지 흔듭니다. 주인공에게서 실제로 그 일이
났습니다 — `appearance_en` 이 옷을 네 벌 나열해서 컷마다 다른 옷이 나왔습니다.
그래서 `outfit` 에는 **여러 벌 나열을 금지**합니다.

돌아가는 길:

1. **스토리** — `w5` 가 새 인물마다 네 항목을 채웁니다. 안 채우면 5단계 게이트가
   되돌립니다 (시키기만 하고 검사하지 않으면 모델이 빼먹고, 빼먹은 건 그림
   단계에 가서야 — 이미 그린 뒤에 — 드러납니다).
2. **저장** — 명부(`series.json`)가 누적하고, 다음 화 프롬프트에
   `외형(고정)` / `옷차림(고정)` / `성격(고정)` 으로 되돌려 줍니다. 3화에서
   머리색이나 옷이 바뀌면 독자에게는 다른 사람입니다.
3. **그림** — 첫 실행이 `supporting.json` 초안을 만들며 명부 값을 그대로 받아
   옵니다. 비어 있으면 사람이 채웁니다 (0원). 채운 사람만, **그 컷 서술에 이름이
   나올 때만** 프롬프트에 붙습니다 — 안 나오는 사람까지 붙이면 모델이 화면에
   없는 인물을 그려 넣습니다.

**P1 의 「그 한 사람」(관계 예외 인물)도 잡습니다.** 이야기에서는 처음부터 있던
인물이라 `new_cast` 에 절대 안 들어가는데, 그림 단계에는 주인공 시트밖에 없어서
그 사람도 낯선 사람입니다 — 가장 자주 나오고 가장 많이 흔들리는데 검사를
빠져나갔습니다. `w5` 가 첫 등장 화에서 그 사람도 `new_cast` 에 적게 했습니다.

**빈 칸이어도 그냥 두지는 않습니다.** 이름만 있는 사람에게는 다른 문구가 붙습니다
— *"생김새는 네가 정하되, 한 번 정하면 이 화 내내 바꾸지 마라. 성별도 바꾸지
마라."* 외형을 지정하지 못해도 **성별이 컷마다 뒤집히는 것은 이 한 줄로 대부분
막힙니다.**

이름 대조는 `cast.json` 과 같은 규칙입니다. 명부에 「하윤재」로 있어도 서술에는
"윤재가", "윤재는" 으로 나오므로 **성을 뗀 형태까지** 봅니다 — 전체 이름만 찾으면
한 번도 안 걸립니다(실제로 7 Scene 중 1곳만 걸렸다가, 고친 뒤 5곳이 됐습니다).

### 그림으로 잇기 — 조건 `S+`

문구로 안 되는 것이 있습니다. 조연에게는 캐릭터 시트가 없어서, **이전에 그려진
모습을 보여 주는 것** 말고는 얼굴을 이어 붙일 방법이 없습니다.

조건 `S+` 는 통합 시트에 **직전 장**을 하나 더 붙입니다. 후보가 1장이면 체인이
깔끔합니다(직전 장 = 그 장의 유일한 결과).

```bash
python run.py --run-id <id> --episode 1 --mode scene -c S+ --style webtoon
```

직전 장을 붙이면 모델이 **레이아웃까지** 따라 그리려 하므로, `extra` 가 "인물
생김새만 보고 배치·구도·배경은 보지 마라"를 못박습니다.

`S` 는 그대로 둡니다 — 둘을 나란히 뽑으면 "직전 장을 붙이면 조연이 실제로
이어지는가"를 잴 수 있습니다.

story-harness 쪽도 고쳤습니다 — `w5` 가 `new_cast` 에 `gender` / `appearance` 를
채우게 했고, 명부(`series.json`)가 그것을 누적해 다음 화 프롬프트에 "외형(고정)"
으로 되돌려 줍니다. 그 run 부터는 초안이 채워진 채로 나옵니다.

### 세로 스크롤이 아니라 만화 페이지로 나올 때

프롬프트는 이미 세 번 말하고 있습니다 — *"Not a comic book page"*, *"no panel
borders, no frames, no gutters"*. 그런데도 흰 여백과 테두리가 나옵니다.

**문구가 아니라 캔버스 문제입니다.** `aspect_ratio: "3:4"` 는 만화책 페이지
비율입니다(세로가 가로의 1.34배). 그 캔버스에 컷 4개를 넣으라고 하면 격자로
쌓을 수밖에 없습니다. 지금은 `9:16`(1.78배)에 `scene.max_cuts_per_scene: 2` 를
둡니다 — 연출이 정한 경계는 살리되 한 장에 몰리는 것만 잘라 나눕니다.

`max_cuts_per_scene` 을 바꾸면 `scenes.json` 캐시가 자동으로 무효화됩니다.

## 검토 화면 (`review.html`) — 읽으면서 피드백

생성이 끝나면 `episode.png` 와 함께 **자동으로 만들어집니다.** `--sheet-only`
로도 다시 만들어집니다 (API 호출 0회).

컨택트 시트는 **후보를 고르는 표**입니다. 조건 x Scene 격자에 후보가 늘어서
있어서 완성본을 통독하기에 맞지 않습니다. 그런데 고칠 것이 실제로 보이는
순간은 **1화를 처음부터 끝까지 읽어 내려갈 때**입니다 — 옷이 바뀌었다, 이 컷은
얼굴이 작다, 여기서 흐름이 끊긴다는 순서대로 봐야 보입니다.

그래서 이 화면은 컨택트 시트와 반대로 만들었습니다:

- 조건 하나, 채택본만. 후보를 나란히 놓지 않습니다
- 읽는 순서 그대로 세로로 (그림 사이에 틈 없이 — 이음매를 보려는 화면이므로)
- 그림 옆에 **그 장에 무엇을 담으려 했는지** — 컷 서술·대사·나레이션·효과음·
  beat·size·작화. 의도와 결과를 나란히 놓아야 "왜 이렇지"가 아니라 "뭘 고치지"가
  나옵니다

### 피드백은 셋으로 나뉩니다 — 고칠 곳이 다르니까

| 칸 | 어디로 가는 피드백 |
| --- | --- |
| 🎨 **그림** | 이 저장소. 옷이 다름, 얼굴이 작음, 서술과 다르게 그려짐 |
| 📖 **스토리** | story-harness. 이 대사 어색함, 이 컷 필요 없음, 훅이 약함 |
| 🧩 **종합** | 둘 다 / 구조. 컷을 더 묶어야 함, 비용, 순서 |

컷마다 그림·스토리 두 칸, 장마다 한 칸(구도·이음매·분위기), 맨 위에 화 전체
세 칸. 한 칸에 섞어 적으면 나중에 무엇을 어디서 고쳐야 하는지 다시 분류해야
합니다.

`Ctrl+Enter` 로 다음 칸으로 넘어갑니다 — 적을 것이 많을 때 마우스로 옮겨
다니면 흐름이 끊깁니다.

## 피드백 칸 — 무엇이 잘못됐는지 적는 자리

채택(`picks.csv`)은 "어느 장이 나은가"만 남깁니다. 정작 고쳐야 할 것은 "왜
별로인가"인데 그건 적을 자리가 없었습니다.

컨택트 시트에 컷/Scene 마다 메모 칸이 있고, 맨 위에 화 전체 칸이 있습니다.
적는 즉시 브라우저에 저장되고, **[feedback.json 내려받기]** → 같은 폴더에
저장하면 다음에 시트를 다시 만들 때 그대로 복원됩니다 (`picks.csv` 와 같은 길).

피드백은 **사람이 보는 기록**입니다. 코드가 읽어서 프롬프트에 자동으로 넣지
않습니다 — 자동으로 밀어 넣으면 무엇을 바꿔서 좋아졌는지 알 수 없게 됩니다.
고칠 것이 정해지면 `config.yaml` 이나 `supporting.json` 을 고쳐서 다시 뽑으세요.

---

## 결과물은 `episode.png` 한 장입니다

만들려는 것은 장면 모음이 아니라 **웹툰 한 편**입니다. 생성이 끝나면 Scene
이미지를 순서대로 **틈 없이** 이어 붙여 `episode.png` 를 남깁니다. 그게
결과물이고 나머지(PNG 여러 장, 컨택트 시트, 뷰어)는 과정입니다.

- 후보가 1장이면 채택 없이 바로 붙습니다 (기본값이 1장입니다)
- 여러 장이면 `picks.csv` 의 채택본을, 기록이 없으면 `c1` 을 씁니다
- 조건을 여러 개 돌렸으면 **이미지가 가장 많이 있는 조건**을 골라 붙입니다
- `--sheet-only` 로 **API 호출 없이 다시 붙일 수** 있습니다 (0원)

이음매를 코드로 보정하지 않습니다 — 겹쳐 페이드하거나 색을 맞추면 잘못이
가려집니다. **이음매가 튀면 그건 프롬프트가 앞뒤 장을 이어 그리지 못했다는
신호**이고, 그 신호는 보여야 다음에 무엇을 고칠지 알 수 있습니다.

### 이음매를 어떻게 잇는가

Scene 을 한 장씩 따로 굽고 세로로 붙이는 구조라, 아무 말도 안 하면 모델은
매번 **자기 안에서 완결되는 그림**을 그립니다. 실제로 그랬습니다 — 이어 붙이니
잔디밭에서 캠퍼스로, 복도로 뚝뚝 끊기고 장 사이에 흰 띠가 생겼습니다.

세 가지로 잡습니다:

1. **이 장은 페이지가 아니라 조각이다** (`scene.composition.rules`) — 그림이
   맨 위·맨 아래 가장자리까지 차야 하고, 흰 여백·테두리·둥근 모서리 금지.
   *"필름 조각처럼 위아래가 잘려 있어야 한다"* 고 못박습니다.
2. **앞뒤 장을 알려 준다** (코드가 자동) — 앞 장의 **마지막 컷**과 뒷 장의
   **첫 컷** 서술만 넘깁니다. 장 전체를 주면 모델이 앞 장을 다시 그리려 듭니다.
   *"위에서 이어진다 — 장소·빛 방향·색보정·시간대를 그대로 가져가되 레이아웃은
   베끼지 마라"*.
3. **직전 장 이미지 첨부** (조건 `S+`) — 문구로 안 되는 것을 그림으로 잇습니다.

거기에 `staging`(장소·시간·조명)과 `mood` 가 화 전체에 고정으로 깔립니다.

## 연출 근거는 어디에 있나

컷 설계 이론(카메라 축·전환·여백·시선·리듬)은 **story-harness 쪽 문서**에
정리돼 있습니다. 이 저장소는 그 설계를 그림으로 옮기기만 하므로, 왜 그렇게
설계됐는지가 궁금하면 그쪽을 보세요.

| 문서 | 무엇 |
| --- | --- |
| `story-harness/docs/webtoon_directing_reference.md` | 연출 이론 리서치 + 하네스 규칙으로의 번역 + **반증 사례** |
| `story-harness/docs/vertical_scrolling_directing.md` | 세로 스크롤 특화 — 거터=시간, 세로 확장 칸, 리빌, 클리프행어 |
| `story-harness/docs/webtoon_directing_2.md` | 샷 스케일·전환 유형 |
| `story-harness/docs/story_movie.md` | 영화 문법의 만화 적용 |

이 저장소가 그 문서에서 직접 가져온 것 하나:

> **패널 시청 시간은 이미지 크기가 아니라 말풍선 텍스트 길이에 비례한다**
> (Ikuta et al. 2023, Sci Rep). "큰 컷 = 느린 템포"는 부분적 통념이고, 대형컷으로
> 독자를 붙잡으려면 **시각 정보 밀도를 같이 올려야** 한다.

그래서 `scene.panel_style.impact` 는 크기만 말하지 않고 *"이 패널은 독자가 멈추라고
만든 것이니 볼 것을 넣어라 — 가장 풍부한 조명과 대기감과 묘사를"* 까지 말합니다.
크게만 만들면 독자는 그냥 지나갑니다.

같은 문서의 경고도 새겨 둘 만합니다 — **여백 픽셀 절대치(100~800px)는 실무
경험칙이지 검증된 값이 아니므로 상대 비율로 다루라.** 이 저장소의 `panel_style`
이 절대 픽셀이 아니라 **상대 가중치**(`height: 0.6 / 1.0 / 1.7 / 2.4`)를 쓰는
이유입니다.

## 누가 무엇을 정하나 — 글자 / 모양 / 보정

이 저장소는 **대사도 나레이션도 쓰지 않습니다.** 글자는 전부 스토리 쪽에서
옵니다. 여기서 정하는 것은 그것이 화면에서 어떻게 보일지입니다.

| 무엇 | 누가 | 어디 |
| --- | --- | --- |
| 대사·나레이션·속마음 **글자** | 스토리 (W7) | `ep01_cuts.json` |
| 효과음 **낱말** | 스토리 (W7) | `sfx` 필드 |
| 말풍선 **모양** | **코드** | `scene.bubbles` (6종) |
| 효과음 **레터링 모양** | **scene_gen** | 프롬프트 5.1 |
| 화면 **보정** | **scene_gen** | `scene.treatment_guide` (어휘) |
| 패널 **내용** | **scene_gen** | 프롬프트 전체 |

### 왜 보정과 효과음을 코드에서 뺐나

둘 다 원래 코드가 `beat` 로 골라 **고정 문구를 박았습니다.** 13컷짜리 한 화를
재 보니 같은 문장이 이렇게 반복됐습니다:

```
"A soft vignette and directional light raking across this element."   4회
"Muted desaturated colour, almost monochrome…"                        3회
"Radial focus lines converging on the subject…"                       3회
```

`build` 비트면 무조건 같은 vignette 였습니다. 그런데 **같은 비트라도 햇빛 드는
잔디밭과 밤 복도는 다른 보정을 받아야 합니다.** 코드는 그 차이를 모릅니다 —
`mood` 를 가진 것은 `scene_gen` 뿐입니다.

효과음은 더 어긋나 있었습니다. `beat` 는 **이야기의 리듬이지 소리가 아닙니다.**
"쿵" 과 "톡톡톡" 이 같은 비트에 있으면 똑같은 레터링을 받았습니다.

### 대신 무엇을 주나 — 규칙이 아니라 어휘

`scene.treatment_guide` 는 박을 문구가 아니라 **감각**을 넘깁니다:

```yaml
treatment_guide:
  intents:                      # 이 비트가 화면에서 무엇을 하려는 것인가
    turn: "the hardest hit on the page; nothing else may compete with it"
    hold: "stop time; the reader should sit in this one a beat longer"
  toolbox: >-                   # 고르라는 목록이 아니라 "이런 것들이 있다"
    vignette, rim light, lens bloom, shallow focus, radial focus lines,
    halftone, film grain, desaturation toward monochrome, …
```

거기에 규칙은 **딱 둘만** 걸었습니다:

- **대부분의 패널은 아무것도 안 받는다.** 보정은 문장부호입니다 — 전부 보정하면
  아무것도 보정으로 안 읽힙니다.
- 같은 장 안에서 연속으로 같은 보정을 쓰지 않는다.

### 코드가 계속 쥐고 있는 것

**말풍선과 그 안의 한글.** 여기는 안 넘깁니다 — 한글이 **정확해야** 하고, 그림을
굽기 전에 `--dry-run` 으로 눈으로 확인되어야 하기 때문입니다. LLM 이 다시 쓰면
"스윽" 이 "스슥" 이 됩니다. 효과음도 **낱말은** 코드가 보장하고 모양만 넘겼습니다.

대신 `scene_gen` 에게 다른 일을 줬습니다 — *"말풍선이 얼굴을 가리지 않게 빈
자리를 남기고, 소리치는 대사와 중얼거리는 대사는 말풍선이 그려지기 전에 이미
다른 그림이게 하라."*

## 글자는 이제 합성으로 갑니다 (효과음·화면 UI 포함)

말풍선 잘림 · 단톡방 문구 안 보임 · 효과음 깨짐은 전부 같은 원인이었습니다 —
**한글을 이미지 모델이 그리고 있었습니다.**

### 효과음도 `lettering` 을 따릅니다 (바뀐 것)

예전에는 `sfx_clause` 가 모드와 무관하게 **언제나** 이미지에 구웠습니다. 효과음은
그림에 녹아드는 레터링이라는 이유였는데, 그러면 `overlay` 로 돌려도 한글이 깨질 수
있는 자리가 하나 남습니다. 지금은 `overlay` 면 효과음도 자리만 비우고 글자는 뷰어가
얹습니다.

### 화면 안 글자(`screen_text`)는 **언제나** 합성입니다

여기는 선택지가 없습니다. 이미지 모델은 한글 UI 를 못 그립니다 — 단톡방 문구를
서술로 넘겼더니 글자가 아예 안 나오거나 뭉개진 획이 나왔습니다.

`screen_ui_clause` 는 **화면을 비워 그리라고** 지시합니다: 화면의 테두리·빛·주변은
그리되 화면 표면은 글자·아이콘 없는 단색 판으로. 그 위에 뷰어가 한글을 얹습니다.
`lettering` 이 `in_image` 여도 마찬가지입니다.

### 말풍선 자리를 미리 비웁니다 (`bubble_zone`)

콘티가 컷마다 글자가 놓일 자리를 정하고(`top`/`bottom`/`left`/`right`/`center`/`none`),
`bubble_zone_clause` 가 그 자리를 비우라고 프롬프트에 넣습니다.

> ⚠️ **이건 보장이 아니라 힌트입니다.** 모델은 무시할 수 있습니다. 잘림을 구조적으로
> 막는 것은 합성 단계이고, 이건 그 앞에서 얼굴 위에 글자가 얹히는 경우를 줄입니다.

### 자동 배치가 생겼습니다 — 다만 초안입니다

오랫동안 자동 배치를 하지 않았습니다. 이유는 정당했습니다: 빈 말풍선이 그림 어디에
있는지 모르는 채로 아무 데나 글자를 얹으면 말풍선 밖에 떨어져 손이 더 갑니다.

그건 **자리를 아무도 모를 때**의 이야기입니다. 지금은 콘티가 `bubble_zone` 을 정하고
그 자리를 비우라는 지시가 생성 프롬프트에도 들어가므로, 그림과 배치가 같은 값을
봅니다. `bubbles.auto_regions()` 가 그 값으로 초안을 만듭니다.

**사람이 그린 사각형이 언제나 이깁니다.** 초안은 `bubbles.json` 에 없는 컷만 채웁니다 —
자동 배치는 "그림이 지시를 따랐다"는 가정이고, 그 가정이 틀렸을 때 고치는 것은
사람이기 때문입니다. `bubble_zone` 이 없는 옛 run 은 초안이 비어 있고 예전처럼
"배치 대기" 목록에 남습니다.

---

## 말풍선 모양 — 코드가 고릅니다

`scene_gen.txt`(LLM)는 이제 **패널 안의 내용만** 씁니다. 말풍선 모양·효과음
꾸밈·화면 보정은 코드가 고릅니다. LLM 에게 맡기면 매번 조금씩 달라져 추적할 수
없고, `--dry-run` 으로 미리 볼 수도 없기 때문입니다.

| 무엇 | 무엇으로 고르나 | config |
| --- | --- | --- |
| 말풍선 모양 | 필드 종류 + 대사 문장부호 + `reader_only` | `scene.bubbles` |
| 효과음 꾸밈 | `render_style` → `beat` | `scene.sfx_styles` |
| 화면 보정 | `beat` | `scene.treatments` |

말풍선은 `normal` / `shout`(`!`) / `whisper`(`…` 나 괄호) / `thought` / `narration`
/ `flashback`(`reader_only`) 중에서 고릅니다. w7 이 컷에 `bubble_shape` 나
`treatment` 를 넣어 주면 그 값이 우선합니다 — 지금은 없어도 됩니다.

### 글자를 누가 그리나 (`scene.lettering`)

- `in_image` (기본) — 대사·나레이션·속마음까지 모델이 그림 안에 그립니다.
  효과음을 이미 그렇게 맡기고 있으므로 같은 논리입니다.
- `overlay` — 말풍선은 빈 껍데기로 그리고 글자는 뷰어가 얹습니다(예전 방식).

한글이 깨지면 `overlay` 로 한 줄만 바꾸면 됩니다. 프롬프트 전체가 같이 바뀝니다.

## 한 장 안의 화면 구성 (`scene.composition`)

패널을 위아래로 쌓지 않습니다. 가장 큰 컷 하나가 **바탕 레이어**로 시트 전체를
덮고, 나머지가 그 위에 테두리 없이 떠서 서로 겹칩니다.

```
BASE LAYER — Panel 4: fills the ENTIRE sheet edge to edge … bleeds off all four edges
OVER THE BASE — Panel 1: sits high on the sheet toward the left, about 55% …
OVER THE BASE — Panel 2: sits on the right at mid height … overlapping the element above
```

자리는 `scene.composition.slots` 가 순서대로 정하고, 크기는 w7 의 `size` 에서
옵니다. `scene.composition.rules` 가 테두리 금지·경계 넘기·배경 잇기를 못박습니다.

## 컷마다 누가 나오는가 (`cast.json`)

이 하네스는 처음에 **등장인물 1명**을 전제로 만들어졌습니다. 외형 문구도
캐릭터 시트도 모든 컷에 똑같이 붙었습니다. 그런데 w7 컷에는 여러 인물이 나옵니다 —
주인공이 없는 컷에 주인공 시트를 붙이면 **조연이 주인공 얼굴로 그려집니다**.

컷마다 주인공이 화면에 있는지 판정하고, 없는 컷에는 **외형 문구·디자인 고정
문구·캐릭터 시트를 모두 붙이지 않습니다** (대신 "주인공은 이 패널에 없다"를
명시합니다). 판정은 이 순서입니다:

1. `cast.json` — 사람이 고친 값. 언제나 최우선
2. `prompts.json` 의 `main_present` — 생성 때 LLM 이 남겼다면
3. 이름 대조 — 컷 서술에 주인공 이름이 있는가 (예비 경로)

3번은 **따옴표 안을 먼저 지우고** 봅니다. 이름이 불리는 것과 그 사람이 화면에
있는 것은 다르기 때문입니다:

```
컷 7  클로즈업. 황후 엘리시아의 옆모습, 입술이 살짝 벌어지며 ‘제라프’라는 이름을 부르려 한다.
      → 화면에 있는 것은 황후입니다. 주인공 없음.
```

첫 실행에서 `cast.json` 초안이 만들어지고, `--dry-run` 이 컷별 판정을 표로
찍습니다. **틀린 줄의 true/false 만 고치면 됩니다 — API 호출 없이 0원으로.**
이미 있는 `cast.json` 은 덮어쓰지 않습니다.

Scene 모드에서는 묶인 컷 중 하나라도 주인공이 나오면 시트를 붙입니다. 나머지
패널의 인물은 조건 문구의 "시트는 주인공에게만 적용" 규칙이 지킵니다.

## 캐릭터 시트 (story-harness 연동)

캐릭터 외형은 이제 **story-harness 의 run 폴더가 기준**입니다. 예전에는
`config.yaml` 의 `character_appearance` 와 `refs/turnaround.png` 를 손으로 채웠고,
스토리 쪽 설정이 바뀌어도 여기는 그대로라 조용히 어긋났습니다.

`--run-id` 를 주면 아래를 **자동으로** 읽습니다. 없으면 예전 방식으로 떨어집니다.

| 읽는 것 | 어디서 | 없을 때 |
| --- | --- | --- |
| 외형 문구 | `p1.json` 의 `appearance_en` | `config.yaml` 의 `character_appearance` → 둘 다 없으면 중단 |
| 조건 `S` / `S+` 레퍼런스 | `charsheet/` 의 채택된 통합 시트(`sheet`) | **중단** |
| 조건 `C` / `D` 레퍼런스 | `charsheet/` 의 채택된 `turnaround` | **중단** |
| 조건 `C+` 레퍼런스 | `turnaround` + `expressions` + `details` | **중단** (조용히 C 로 흉내 내지 않습니다) |
| 디자인 고정 문구 | `p1.json` 의 `design_details` / `color_palette` | 안 붙음 |
| 조연 인물 카드 | `webtoon/series.json` 의 명부 → `supporting.json` | 빈 칸 (사람이 채움) |

**통합 시트(`sheet`)와 3장짜리(`turnaround`/`expressions`/`details`)는 담는 정보가
같습니다.** 통합 쪽이 호출이 1/3 이고, 한 장 안에서 그린 것이라 시트끼리의 그림체
흔들림이 없습니다. `--split` 은 3장을 나란히 놓고 "첨부를 늘리면 일관성이 실제로
개선되는지"를 잴 때만 쓰세요 — 개선이 없으면 통합 한 장이 맞습니다.

`design_details` / `color_palette` 는 `style_suffix` 와 **같은 방식으로 코드가**
프롬프트 끝에 박습니다 (`config.yaml` 로 끌 수 없습니다). 턴어라운드 이미지 한
장은 "대충 이런 사람"까지는 전하지만 "왼쪽 소매에만 노란 반사띠 두 줄"은 전하지
못하기 때문입니다. 전문은 `--dry-run` 으로 확인하세요.

### 두 번째 주연("그 한 사람") 시트 — 주인공과 독립적으로 첨부됩니다

지금까지 시트는 주인공 1명 전용이었습니다. `story-harness` 에서
`python story.py --charsheet --run-id <id> --second-lead` 로 뽑은 시트가
`runs/<id>/charsheet_2nd/` 에 있으면, `charsheet.load_second_lead()` 가 이를 읽어
컷/장면 첨부에 자동으로 더합니다 — **조건의 `sheets:` 선언과 무관하게**, 그 인물이
실제로 나오는 컷에만 붙습니다.

- 등장 판정은 주인공과 같은 이름 대조(`cast.name_keys`/`cast.from_cuts`)를 쓰되,
  `cast.json` 파일은 다시 쓰지 않습니다 — 그 파일은 주인공 전용 override 라서,
  같은 파일에 두 사람 몫을 섞으면 나중 판정이 먼저 것을 덮어씁니다. 그래서 지금은
  이름 대조 결과를 그대로 씁니다(틀리면 고칠 파일이 아직 없습니다).
- 주인공과 그 한 사람이 같은 Scene 에 함께 나오면 레퍼런스 이미지가 두 장
  첨부됩니다. 이때 프롬프트에 "몇 번째 이미지가 누구 전용인지" 를 코드가
  못박습니다(`cond_extra` 의 second_lead 문구) — 안 그러면 모델이 두 얼굴을 섞습니다.
- `charsheet_2nd/` 가 없으면 그냥 조용히 빈 손으로 넘어갑니다 — 지금까지 하던 대로
  `supporting.json` 의 글자 고정만 적용됩니다. 필수가 아닙니다.

### 존 배경 자산 — `Cut.zone` 이 있으면 자동으로 붙습니다

`story-harness` 에서 `python story.py --zonesheet --run-id <id>` 로 뽑은 배경이
`meta.json` 의 `zonesheet` 키에 등록돼 있으면, `charsheet.load_zonesheet()` 가
이를 읽습니다. Scene 모드에서 묶인 컷이 **전부 같은 `zone`** 이면
(`scenegen.scene_zone`) 그 존의 배경을 레퍼런스로 첨부합니다 — 인물 시트와
독립적이라, 그 컷에 누가 나오든 상관없이 붙습니다. 컷마다 존이 갈리면(예전 run
처럼 `zone` 이 비어 있거나, 한 Scene 안에서 장소가 바뀌면) 붙이지 않습니다 —
배경 하나를 잘못 붙이는 것이 안 붙이는 것보다 나쁩니다.

이 두 자산(주연 시트·존 배경)은 조건 `S+`(직전 장 이미지)와 **경쟁하지 않고
보완합니다** — `S+` 는 "인물이 방금 전과 이어진다"를, 존 배경은 "이 장소는 항상
이렇게 생겼다"를 맡습니다. 둘 다 켜 두면 인접 장면 이음매와 장소 일관성을
동시에 잡습니다.

### 시트가 없으면 멈춥니다 (조건 S / S+ / C / C+ / D)

`sheets:` 를 선언한 조건은 **그 run 의 시트**만 씁니다. 없으면 실행이 멈춥니다.

예전에는 `config.yaml` 의 `refs`(`refs/turnaround.png`)로 조용히 떨어졌습니다.
그 자리에는 지난 run 의 시트가 남아 있기 마련이고, 조건 문구는 "얼굴·머리·체형·
의상을 첨부 시트와 **똑같이** 하라"고 명령합니다 — 즉 **다른 사람을 똑같이
그리라고** 시키게 됩니다. 실제로 민시하 13컷에 제라프 턴어라운드가 붙어 한 화가
통째로 날아갔습니다. 화면에 한 줄 찍히기는 했지만 경고가 아니라 안내처럼
보였고, 결과 이미지를 보기 전에는 알 수 없었습니다.

시트 없이 그림체만 먼저 보려면 **조건 A** 를 쓰세요 (첨부 없음).

### style_suffix — 두 하네스의 유일한 공통 기준점

`--charsheet` 가 이 값을 읽어가므로, 시트와 컷은 같은 문구를 봅니다.
실행할 때마다 **시트를 만들 때의 값과 지금 config 의 값이 같은지** 확인하고
다르면 경고합니다. 어긋난 채로 뽑으면 시트가 가리키는 그림체와 컷이 향하는
그림체가 다른 곳이 됩니다.

같아도 안심할 수는 없습니다 — **시트는 OpenAI 이미지, 컷은 Gemini** 입니다.
같은 문구를 줘도 손이 다르면 그림체가 다릅니다. 그래서 시트가 붙은 실행에서는
두 모델 이름을 항상 같이 찍습니다. 시트는 *무엇을 그릴지*의 기준이지
*어떻게 그릴지*의 보증이 아닙니다.

**story-harness 에는 `--style` 이 없습니다.** `--charsheet` 는 이 저장소
`config.yaml` 의 **`style_default`** 를 읽어 시트를 그립니다. 그러니 시트를 뽑기
**전에** `style_default` 를 그 화에 쓸 그림체로 맞추세요. 컷은 `--style` 로 덮을
수 있지만 시트는 그럴 수 없습니다.

> 참고 — 예전에 `story.py` 의 YAML 리더가 `styles.<이름>` 을 문자열로 보고
> `"normal: >-"` 이라는 글자를 그림체 문구로 읽어 갔습니다 (콜론 뒤 `\s*` 가
> 줄바꿈을 먹어 다음 줄을 값으로 집었습니다). 시트가 사실상 그림체 지시 없이
> 뽑히던 문제이고, 지금은 고쳤습니다.

### story-harness 쪽에 필요한 파일 형식

읽는 쪽은 아래를 모두 받아줍니다. 어느 것으로 읽었는지는 항상 화면에 찍힙니다
(`[charsheet] ... · 출처 ...`).

```
runs/<run_id>/
  p1.json                appearance_en / design_details / color_palette / expression_set
  charsheet/             채택된 시트 이미지
  charsheet_picks.json   {"picks": {"turnaround": {"file": "charsheet/turnaround_c2.png"}, ...}}
                         또는 {"turnaround": "charsheet/turnaround_c2.png", ...}
  meta.json              {"charsheet": {"style_suffix": "...", "model": "gpt-image-1"}}
```

`charsheet_picks.json` 이 없으면 `meta.json` 의 `charsheet.paths` 를, 그것도
없으면 `charsheet/` 안의 **파일 이름**(`turnaround` / `expressions` / `details`
가 들어간 이미지)으로 찾습니다. 마지막 수단이므로 채택 기록을 남기는 편이 낫습니다.

두 자산은 형식이 훨씬 단순합니다 — story.py 가 쓰는 형태 하나만 읽습니다 (옛
형식을 받아줄 필요가 없습니다, 이번에 새로 생긴 경로라서):

```
runs/<run_id>/
  charsheet_2nd/lead.json        appearance_en / design_details / color_palette / expression_set
  charsheet_2nd/                 채택된 시트 이미지 + charsheet_picks.json
  meta.json                      {"charsheet_second_lead": {...}}   ← "charsheet" 키와 별개
  zonesheet/<zone_id>/bg_c1.png  존 배경
  meta.json                      {"zonesheet": {"<zone_id>": {"path": "..."}}}
```

### 콘티에서 받는 연출 (`ep{NN}_cuts.json`)

`storyload.py` 가 읽고 `scenegen.py` 가 프롬프트로 옮깁니다. 없으면 없는 대로
돌아갑니다 — 옛 run 은 그대로 로드됩니다.

| 필드 | 여기서 무엇이 되는가 |
| --- | --- |
| `description` | 패널 영어 서술의 원본 |
| `dialogue` `narration` `thought` `sfx` | `bubble_clause` · `sfx_clause` — 말풍선/상자/레터링 |
| `size` | Scene 레이아웃(칸 비율) |
| `beat` | `treatment_clause` — 집중선·빛번짐 같은 화면 보정 |
| `gaze` | `scene_gen.txt` 규칙 3.5 — 패널의 시선 방향 |
| `render_style` | `scene.panel_render` 문구. `normal` `sd` `emphasis` `bleed` `breakout` |
| `shot` `angle` | `SHOT_EN` / `ANGLE_EN` 로 영어 샷 용어가 되어 패널마다 박힙니다 (규칙 3.6) |
| `speaker` | 말풍선 꼬리를 누구에게 붙일지 |
| `scenes[].what` `.mood` | **규칙 3.4** — 그 Scene 패널 전체의 공기 |
| `zone` | 묶인 컷이 전부 같은 값이면(`scenegen.scene_zone`) 그 존의 배경 자산을 레퍼런스로 첨부 |
| `characters_in_frame` | 컷마다 누가 화면에 있는가 (콘티가 필드로 준다 — 예전에는 서술에서 이름을 찾았습니다) |
| `composition` `composition_note` | `composition_clause` — 오버숄더·프레임인프레임 같은 구도를 영어 지시로 |
| `screen_text` | `screen_ui_clause` — 화면을 **비워** 그리게 하고 글자는 뷰어가 얹습니다 |
| `bubble_zone` | `bubble_zone_clause`(그 자리를 비우라는 지시) + `bubbles.auto_regions`(합성 자리 초안) |

화 단위로는 `setting`(place / time / weather / light)이 `staging_text()` 로 들어가
화 내내 고정됩니다.

> **`mood` 가 가장 중요합니다.** 컷 서술은 "무엇이 보이는가" 만 말합니다. "어떤
> 공기로 그릴 것인가" 는 `mood` 에만 있고, 이게 없으면 패널마다 톤이 새로 정해져
> 같은 장면인데 한 컷은 서정적이고 다음 컷은 스릴러가 됩니다.

> ⚠️ **`shot` 필드와 규칙 2 는 한 몸입니다.** 예전 규칙 2 는 샷을 *"the shot
> signalled by the Korean text"* 로 **서술에서 짐작**했습니다. 콘티가 서술에서
> 카메라 낱말을 빼내 필드로 옮겼으므로, 필드를 안 읽으면 샷 신호가 아예
> 사라집니다. 둘은 같이 바뀌어야 합니다.

> ⚠️ `storyload.RENDER_STYLES` 에 없는 값은 `_one_of` 가 조용히 `normal` 로
> 깎습니다. 콘티가 `render_style` 값을 늘리면 여기와 `scene.panel_render` 를
> 같이 늘려야 합니다 — 실제로 `bleed`/`breakout` 이 한동안 그렇게 사라졌습니다.

## 토큰과 비용 — 호출할 때마다 남습니다

API 를 부를 때마다 그 호출의 토큰과 비용이 `log.jsonl` 에 함께 적힙니다. 실행이
끝나면 `usage.csv`(호출별)와 `usage.json`(합계)이 다시 만들어집니다. 실패한
호출도 남습니다 — 토큰은 청구되기 때문입니다.

호출 하나마다 남는 것:

| 열 | 무엇 |
| --- | --- |
| `call_id` | 이 화의 몇 번째 호출인가 (`ep1-0007`). `log.jsonl` 에서 프롬프트 원문을 찾는 열쇠 |
| `kind` | `image` / `prompt_gen` / `cut_split` / `scene_gen` / `verify_scene_gen` |
| `condition` `cut_number` `candidate` `attempt` | 어떤 요청이었나 (재시도까지 따로) |
| `provider` `model` | 어느 모델이 받았나 — 이미지와 텍스트는 다른 모델입니다 |
| `tokens_in` `tokens_out` `tokens_thought` `tokens_total` | 실제 토큰. 입력은 `_text` / `_image` 로, 출력은 `_image` 로 더 쪼개집니다 |
| `cost_basis` | `tokens`(실단가 계산) 인가 `flat`(고정 어림값) 인가 |
| `est_cost_usd` `est_cost_krw` | 그 호출의 비용 |
| `attachments` | 첨부 장수. 입력 토큰이 튀었으면 대개 여기가 원인입니다 |

`usage.json` 은 종류별·모델별·조건별 합계와 **가장 비쌌던 호출 5건**을 담습니다.
조건 A/C/D 중 어디에 돈이 갔는지, 이미지와 텍스트 중 어느 쪽이 컸는지가 파일
하나로 보입니다.

### 실제 단가로 계산하려면 (`pricing.rates`)

기본값은 **고정 어림값**입니다 — 이미지 1장 = `provider.cost_per_image_usd`,
텍스트 1회 = `text.cost_per_call_usd`. 첨부를 3장 붙였든 1장 붙였든 같은 값이
찍히고, thinking 토큰은 반영되지 않습니다.

`config.yaml` 의 `pricing.rates` 에 100만 토큰당 단가를 채우면 그때부터 호출마다
실제 토큰으로 계산합니다:

```yaml
pricing:
  rates:
    gemini-3-pro-image:       # 이름은 앞부분만 맞으면 됩니다
      input: <...>
      output: <...>
      output_image: <...>     # 이미지 출력 토큰 단가가 따로 있는 모델만
      thought: <...>          # 없으면 output 단가를 씁니다
```

**숫자는 직접 채우세요.** 요금표는 모델과 시점에 따라 다르고, 임의의 값이 들어
있으면 틀린 비용이 맞는 비용처럼 보입니다. 그래서 비워 둔 채로 두었습니다.
아직 어림값으로 매겨진 호출이 몇 건인지는 `usage.json` 의 `calls_priced_flat`
에 나옵니다 — 단가를 다 채우면 0 이 됩니다.

### 예전 실행분

토큰을 최상위에 적기 전에 돌린 줄도 `provider_meta.usage` 에 원본이 남아
있습니다. 집계할 때 거기서 채워 읽으므로 예전 화도 같은 표에 들어옵니다
(`log.jsonl` 파일 자체는 고치지 않습니다). 원본조차 없는 줄은
`calls_without_tokens` 로 셉니다.

## `--style-lock` — Scene 사이 그림체가 유지되는가 (0원)

```bash
python run.py --style-lock --run-id 20260803T223106-38684d --episode 1 -c S+
```

기존 스타일 실험은 "캐릭터 1명 × 장면 1개 × 6회 반복"으로 스타일 문구를 골랐습니다.
그건 **한 장 안에서** 그 문구가 먹히는지를 본 것입니다. 화 전체를 이어 읽을 때
Scene 1 과 Scene 4 가 같은 사람 손에서 나온 것으로 보이는가는 검증한 적이 없습니다.
통독 시 그림체가 제각각으로 보이는 원인일 수 있습니다.

이미 뽑아 둔 `scene_<조건>/` 의 채택본만 읽습니다. **추가 생성 없음.**

**출력**

- `outputs/<id>/ep1/style_lock.html`
  - Scene 을 세로로 나란히 배치
  - **[얼굴만 크롭]** — 각 Scene 에서 얼굴만 잘라 **가로로** 붙여 봅니다.
    그림체 차이는 얼굴에서 제일 먼저 드러납니다. 세로로 떨어져 있으면 눈이
    기억으로 비교하지만, 옆에 두면 눈매 각도와 코 생략 정도가 바로 보입니다.
  - **[확대]** — 원본 픽셀에 가깝게. 선 굵기·채색 질감 확인용
  - Scene 옆 체크 항목: 선 굵기 / 채도·명도 톤 / 얼굴 양식화 정도 / 배경 디테일 밀도
- `outputs/<id>/ep1/style_score.csv` — 빈 채점표
  (`scene_no, 선굵기, 채도톤, 얼굴양식화, 배경밀도, 종합`, 값은 **Y/N**)

**얼굴 자리는 코드가 모릅니다.** 얼굴 검출을 넣으면 의존성이 늘고, 이 하네스는
그걸 감당할 물건이 아닙니다. 처음 열면 어림잡은 상자가 놓여 있습니다 — 정답이
아니라 출발점입니다. **[크롭 편집]** 을 켜고 이미지 위에 끌어 그린 뒤
`style_faces.json` 으로 내려받아 저장하세요.

**점수(1~5)는 쓰지 않습니다.** "7점"은 다음에 뭘 고칠지 알려주지 않지만
"배경밀도 N"은 알려줍니다. CSV 에 숫자를 적으면 다시 읽을 때 버려집니다.

## `--verify-all` — 한 벌로 네 가지를 동시에 검증

```bash
python run.py --verify-all --run-id <id> --episode 1 -c S+ --dry-run   # 프롬프트만
python run.py --verify-all --run-id <id> --episode 1 -c S+             # 실제 생성
```

> **지금 실행하지 마세요.** 스토리 하네스의 W7 수정(컷에
> `size` / `gap_after` / `gaze` / `beat` / `scene_break` 필드 추가)이 끝난 뒤에
> 실행합니다. 지금 뽑으면 컷 서술이 바뀌면서 이 한 벌이 통째로 버려집니다.
> 그때까지는 `--dry-run` 으로 프롬프트 조립만 확인하세요.

**왜 통합하나.** 그림체·말풍선·효과음을 각각 따로 검증하면 생성 비용이 세 번
나갑니다. 그런데 이 셋은 **같은 이미지**로 동시에 잴 수 있습니다.

- 말풍선/효과음 — 새 `scene_gen.txt` 규칙으로 뽑은 이미지에서 바로 확인
- 그림체 — 그 Scene 들은 서로 다른 장면이므로 그대로 편차 측정이 됨
- 통독 — 그 Scene 들을 세로로 이어 붙이면 그게 곧 읽는 화면

**동작**

- Scene 전체를 현재 `prompts/scene_gen.txt` 로 **후보 2장씩** 생성
  (채택용 3장이 아닙니다 — 여기서 고를 것이 아니라 **잴** 것이라서요.
  `config.yaml` 의 `scene.verify_candidates_per_scene` 로 조절)
- 기존 `scene_<조건>/` 을 덮지 않고 **`verify/` 에 따로** 저장.
  패널 서술도 `verify/scenes_verify.json` 으로 따로 남습니다
- 실행 전 호출 수·비용을 보여주고 `y/N` 을 묻습니다
- 이미 뽑아 둔 파일은 다시 뽑지 않습니다 — 같은 명령을 다시 실행하면
  화면만 다시 만듭니다 (0원)

**출력** `outputs/<id>/ep1/verify.html` — 탭 4개

| 탭 | 보는 것 |
| --- | --- |
| ① 말풍선/효과음 | Scene 별 후보를 크게. 다섯 가지를 Y/N 으로 |
| ② 그림체 | `--style-lock` 과 같은 화면 (얼굴 크롭·확대·4개 항목), 대상만 `verify/` |
| ③ 통독 | **실제 Scene 뷰어**를 그대로 띄웁니다. 말풍선 편집·자동 핏·넘침 경고·`bubbles.json` 내려받기가 전부 살아 있습니다 |
| ④ 채점 | `verify_score.csv` 내려받기 |

②는 **한 장 안이 아니라 Scene 과 Scene 사이**를 봅니다. 한 이미지 안의 패널끼리는
같은 호출에서 같이 그려졌으니 일관된 게 당연합니다 — 진짜 문제는 서로 다른
호출로 나온 Scene 들 사이입니다. 화면에도 그렇게 적혀 있습니다.

`verify_score.csv` 열 (전부 **Y/N**):

```
scene_no, 말풍선존재, 말풍선빈칸, 말풍선크기, 얼굴가림, 효과음한글,
          선굵기, 채도톤, 얼굴양식화, 배경밀도, 통독종합
```

네 탭의 체크는 **한 표의 열**입니다. 어느 탭에서 눌러도 같은 칸에 모입니다.

## 실패 시 대안

검증에서 N 이 나왔을 때 무엇을 바꿀지 미리 정해 둔 것입니다.
막힌 자리에서 즉흥으로 정하면 변수가 두 개씩 움직여 비교가 깨집니다.

| 증상 | 대안 |
| --- | --- |
| 말풍선 안에 뭉개진 글자가 채워짐 | 프롬프트에 `completely blank, no text of any kind` 강화 → 그래도 안 되면 말풍선도 CSS 오버레이로 회귀 |
| 말풍선이 인물 얼굴을 가림 | `scene_gen.txt` 에 "말풍선은 인물 얼굴을 가리지 않는 위치" 규칙 추가 |
| 효과음 한글이 심하게 깨짐 | 효과음만 SVG 텍스트 오버레이로 전환 (기울기·왜곡을 줘서 레터링 흉내) |
| Scene 간 그림체 편차가 큼 | 턴어라운드 외에 **스타일 레퍼런스 이미지**를 추가 첨부하는 조건 E 를 만들어 비교 |
| 특정 장면(야간·화재)에서만 그림체가 무너짐 | 프롬프트에서 조명 지시를 스타일 문구 **뒤로** 옮기고 재시도 |

## 설정

`config.yaml` 만 고쳐서 재실행합니다. 모델 이름과 API 키는 `.env` 에 있습니다
(`GEMINI_API_KEY` / `GEMINI_TEXT_MODEL` / `GEMINI_IMAGE_MODEL`, `.env.example` 참고).

`character_appearance` 는 이제 **예비 경로**입니다 — 기준은 `p1.json` 의
`appearance_en` 입니다 (위 "캐릭터 시트" 참고). 둘 다 없으면 중단됩니다.
이 문구와 `style_suffix`, 그리고 시트의 `design_details` / `color_palette` 는
코드가 모든 프롬프트에 강제로 붙입니다. LLM 은 장면 서술만 씁니다.

조건 비교 도중에 `style_suffix` / `global_suffix` / 레이아웃을 바꾸면 이전 실험과의
비교가 깨집니다.
